# TideWall 3D — Tech Notes

## Stack
- **Unity 6000.5.10f1** (Unity 6.5), **URP** 17.5, **Input System** 1.20, UGUI for HUDs.
- **Blender 5.2** generates every model from a Python script (`Blender/generate_models.py`).
- No third-party packages. All sound is synthesized at startup; all UI is built in code.

### Why Unity over Godot
Both were considered. Unity won on four counts:
- **Split screen and controllers:** the Input System gives per-player device pairing and broad controller support (Xbox, PlayStation, Switch Pro, HID joysticks) out of the box.
- **3D performance:** URP's Forward+ handles the many night lights (torches, lanterns, flashes) and the split-screen cameras well.
- **Online later:** Netcode for GameObjects is available when online play is added.
- **Tooling here:** the editor was already installed and licensed on this machine, so it builds and tests headlessly.

## Runtime architecture
```
GameManager  (boots itself into any scene via [RuntimeInitializeOnLoadMethod])
 ├─ GameDatabase / PhaseCycle    data (Resources, or code defaults if the assets are missing)
 ├─ World (WorldBuilder)         ground, sea, Wall, stalls (Interactables), torches, lighthouse
 ├─ PhaseManager                 runs the PhaseCycle: enter, blend lighting, check end conditions, advance
 ├─ WaveDirector                 spends the phase's budget on enemy packs across waves (50% rush rule)
 ├─ PlayerManager                InputSystem.onAnyButtonPress → Join → Player + PlayerCamera + PlayerHud; split-screen rects
 ├─ Fx / Sfx                     shared particle systems, pooled tracers and lights; synthesized clips
 └─ Enemies (static list)        Enemy components, each with Limb components on its Limb_ parts
```

- **Enemies don't use physics to move.** They steer on the ground height (`Arena.GroundY`), are separated from each other, and are clamped behind the wall line. Their colliders (one box per model part) are **triggers**, used only by shots, melee and explosions. Severed limbs switch to non-trigger colliders plus a `Rigidbody` and fly off.
- **Shots** go from the muzzle toward `Player.AimPoint`, the 3D point under the player's reticle. For mouse players that's a camera ray through the cursor; for gamepads, a point along the stick direction, with aim assist toward enemies. `Physics.RaycastNonAlloc` with triggers included; the wall and players are skipped (bullets clear the wall top).
- **Players** use `CharacterController`. Each has its own `InputActionMap` filtered to its devices (`PlayerControls`); keyboard and mouse join together.
- **Per-player UI**: each HUD is a `ScreenSpaceCamera` canvas on that player's camera, so it fits their viewport.
- **Look**: phases blend sun, ambient, fog, sky colour and night lights. Enemies get per-renderer property blocks: `_Smoothness` follows wetness, and `_BaseColor` flashes white on hits.

## Data assets
`GameDatabase` and `PhaseCycle` are ScriptableObjects in `Assets/Resources/Data`. Their defaults are in code (`FillDefaults()`); the setup step writes them as assets the first time.
- Tune by editing the assets in the Inspector.
- If you change a default in code, run **TideWall → Reset Data To Defaults** (or edit the asset too). The asset wins at runtime (CLAUDE.md R1).

## Model pipeline
```bash
blender --background --factory-startup --python Blender/generate_models.py -- <repo root>
```
The Blender executable on this machine is `C:\Program Files (x86)\Steam\steamapps\common\Blender\blender.exe`. The script writes `Assets/Resources/Models/<Name>.fbx` (FBX, -Z forward, Y up, transforms baked). The `ModelImport` postprocessor turns off animation, cameras and lights and keeps the flat normals.

The website's `.glb` models (`Blender/source/`) are imported, scaled to a target size and set on the ground. Their duplicate vertices are welded, and anything over ~8k faces is decimated. Welding has to come first: the Glizzy Monster sculpt is stored as split triangles, and decimating it without welding shreds it. That sculpt is also untextured white, so the script colours it like a sausage.

Conventions (CLAUDE.md R4–R6): front faces -Y in Blender; `Limb_<Part>` objects have their pivot at the joint; `Socket_<Name>` empties mark hands and muzzles; a material named `coat` is recoloured per player.

The **tests** boot the real game, join players with `InputSystem.AddDevice<Gamepad>()`, and cover: lobby boot, joining and split-screen rects, stick movement, the full phase cycle (day advances), limb severing and corpse value, selling at the fishmonger, condiments and the ??? sauce (including a forced jackpot), gas-can explosions, and every enemy behaviour running for 6 s. ## Performance notes
- One shared `ParticleSystem` per effect type: drips, gore, sparks, smoke, fire, splash, ink, bubbles, debris. Calls are `Emit`-style, never per-enemy systems.
- Tracers (`LineRenderer`) and flash lights are pooled.
- `GameDatabase.maxAlive` caps live enemies (70).
- The sea is a CPU-animated grid (~4k vertices).
- Physics queries use non-alloc buffers. Explosions use their own buffers, because they can fire inside a shot or swing loop when a gas can goes off.

## Online multiplayer (future)
Only local split screen is implemented. To add online play with **Netcode for GameObjects**:
1. **Server authority:** the host owns `WaveDirector`, `Enemy` simulation, the `Wall`, coins and team upgrades, and `PhaseManager`. Clients send input; enemies replicate as `NetworkObject`s with position, hp and severed limbs. Corpse and limb physics can be client-side cosmetics.
2. **Players:** `Player` becomes a `NetworkBehaviour`. Input stays local (a `PlayerControls` per local player), and shots and melee are sent as RPCs carrying the aim point, so the server applies `Combat`.
3. **Couch + online mix:** each machine can still have 1–4 local players in split screen; every local player is its own network player.
4. **Randomness:** the server rolls the ??? sauce, gas-can chances and wave composition, then broadcasts the results.
