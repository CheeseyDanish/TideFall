# TideWall 3D — Tech Notes

## Stack
- **Unity 6000.5.10f1** (Unity 6.5), **URP** 17.5, **Input System** 1.20, UGUI + **TextMeshPro** for HUDs and menus.
- **Unity Transport** 2.7 (UDP) for online play, **Unity Relay** (Multiplayer Services 2.4 + Authentication) for join codes.
- **Blender 5.2** generates every model from a Python script (`Blender/generate_models.py`).
- Sounds are formulas (`SfxSynth`) baked into WAV files by the editor setup. HUDs and menus are built in code (`Ui` helpers); the level is a normal scene.

### Why Unity over Godot
Both were considered. Unity won on four counts:
- **Split screen and controllers:** the Input System gives per-player device pairing, broad controller support (Xbox, PlayStation, Switch Pro, HID joysticks) and interactive rebinding out of the box.
- **3D performance:** URP's Forward+ handles the many night lights (torches, lanterns, flashes) and the split-screen cameras well.
- **Online:** .NET sockets work the same in the editor, in tests and in builds, so online play is testable headlessly.
- **Tooling here:** the editor was already installed and licensed on this machine, so it builds and tests headlessly.

Conventions: one MonoBehaviour or ScriptableObject per file, named after it (Unity needs this to save them in scenes and
assets); big classes are `partial` and split by topic (`Player.Movement.cs`…); no `Resources` folder (TextMeshPro keeps

## Runtime architecture
```
TideWall scene (Part I; a Part II stage scene has the same shape with an Expedition for the World)
 ├─ TideWall (GameManager)       references the ContentLibrary; states MainMenu → Playing → GameOver
 │   ├─ GameDatabase / PhaseCycle    data (from the library, or code defaults if missing)
 │   ├─ PhaseManager                 runs the PhaseCycle: enter, blend lighting/sky/fog, autosave, card drafts, end conditions
 │   ├─ WaveDirector                 spends the phase's budget on enemy packs across waves, loading them onto Breakers
 │   ├─ TidalCards                   the draft and vote, active cards and their modifiers, exclusive effects
 │   ├─ PlayerManager                drop-in joining → Player + PlayerCamera + ViewModel + PlayerHud; split screen; cursor
 │   ├─ MainMenu (+ MenuScenery)     the keep-window title screen and its menus
 │   └─ Fx / Sfx                     shared particles, pooled tracers and lights; sounds (relayed online)
 ├─ World                        the level, saved in the scene: Sun, ground, Sea (Water), Wall (sections, gatehouses),
 │                               Powerplant, Town (stalls, vendors, bell, torches), Keep, Lighthouse, Beach, clouds, bounds
 └─ Post Processing (Volume)
Spawned while playing: players, creatures (Enemy + Limb), corpses, loot, defences, breakers — built from the data
Net.Host / Net.Client            online play (DontDestroyOnLoad, survive "try again" reloads)
```

- **The level** is generated by `WorldBuilder` in the editor (TideWall → Rebuild World In Scene, `WorldBaker`) and saved in the scene; models stay linked to their FBX assets, generated meshes/materials are saved under `Content/Generated`. After that the scene is the source of truth: edit it in Unity. At start `World.Init(db)` sets hit points and vendor lines from the data, so tuning never needs a scene change. Things that only exist during play (players, creatures, loot) are spawned from the data (`EnemyDef`, `FoodDef`…) by code.
- **Levels**: the GameManager finds the scene's `Level` (`gm.Level`). `World` is Part I's (`gm.World`, with `gm.Wall` and `gm.Plant`); `Expedition` is a Part II stage's (`gm.Expedition`, `gm.Assault`; no wall or plant, so code that touches them checks `gm.World != null`). A level answers what creatures head for (`Goal`, `FlyerTarget`), where players (re)spawn, where building is allowed (`BuildRule`), the HUD's status line and bar, and carries its own online state (`WriteNet`/`ReadNet`, after the players in every snapshot).
- **Content**: `Content.Use(library)` (called by the GameManager) indexes the library; code asks `Content.Model(name)`, `Content.Material(name)`, `Content.Sounds`. `TideWall → Setup Project` adds new FBX/WAV files to the library automatically.
- **A run** starts from the main menu (`GameManager.StartRun(save, slot)`), or when a player joins while the menu is up (tests, capture: an unsaved run). "Try again" and a host's restart reload the scene with a `GameManager.Pending` run request.
- **Enemies don't use physics to move.** They steer on the ground height (`Arena.GroundY`), are separated from each other, and are clamped behind the wall line except where a section is breached (`Wall.IsOpen`). With no player in reach they follow `World.Goal`: the wall section in front of them, or the nearest breach and then the powerplant. They arrive riding a `Breaker` (the wave sets their position until it breaks). Each kind's animation is procedural: `AnimateLimbs` (limb rotations) and `PoseRoot` (the model root's bob, roll and squash; behaviours only set its ingredients: hop, puff, flop, roll). Their colliders (one box per model part) are **triggers**, used only by shots, melee and explosions. Severed limbs switch to non-trigger colliders plus a `Rigidbody` and fly off.
- **Players** use `CharacterController`. Buttons are read through `Player.Held/Pressed(Btn)`; for a local player that's their `PlayerControls` (an `InputActionMap` filtered to their devices; keyboard and mouse join together), for an online player it's `RemoteInput`.
- **Per-player UI**: each HUD is a `ScreenSpaceCamera` canvas on that player's camera, so it fits their viewport. HUD canvases are on the **HUD** sorting layer (after Default), so world text never draws over them; stall signs also fade out when you are next to them (`Billboard.fadeNear`). The main menu is one screen-space overlay canvas.
- **Look**: phases blend sun, ambient, fog, sky colour and night lights. Enemies get per-renderer property blocks: `_Smoothness` follows wetness, and `_BaseColor` flashes white on hits.

### Views (first and third person)
- `Player.Yaw/Pitch` are the look direction in both views: mouse / right stick turn it, movement is relative to the yaw, the body faces it, and the aim ray goes through the crosshair (screen centre). First person puts the camera at `Player.EyePos`. Third person puts it at a head pivot plus `PlayerCamera.Shoulder` (right, up, back) in the look's frame, pulled in front of walls and ground by a sphere cast (`PlayerCamera.Clear`, ignoring creatures, players and loose things).
- Aiming is split in two: `LocalAim()` turns this machine's camera + controls into an `AimSample` (the crosshair's ray; in third person it leaves the camera and starts level with the sailor, so nothing between camera and sailor is aimed at); `ResolveAim(AimSample)` raycasts it into `AimPoint`/`AimDir` and applies aim assist. Online players send their `AimSample`, so the host resolves exactly what they saw. Shots leave the muzzle (the view model's in first person, the gun model's in third) for the `AimPoint`.
- Layers: each player's body is on layer `8 + index`; their view model on `12 + index`; their name tag on `16 + index`. A first-person camera hides its own body layer; every camera hides other players' view model layers and its own name tag (`PlayerCamera.Mask`, `SpectatorMask`).
- Shots in first person leave from a point bottom-right of the eyes (`Player.MuzzlePosition`) so tracers line up with the view model.
- FOV: the setting is the vertical FOV on a 16:9 screen; wider split-screen strips keep its horizontal width (`PlayerCamera.FirstPersonFov`).
- **Reload minigames** (`Players/ReloadGame.cs`): a plain class the (host-side) player owns while reloading: `Begin(ReloadDef, time, mag)`, `Update(dt, ref ammo, mag)` (true when done; per-round styles load into `ammo`), `Press`, `Release`. `Player.StartReload/FinishReload` wire it to the Reload button (press, and release edge for Pressure); `PerfectBonus` multiplies gun damage until the magazine is empty. Numbers: `GameDatabase.reloads` (`ReloadDef`, the 2D game's RELOADS) and `GunDef.reloadStyle`. Online, `NetPlayerState` carries the game (`ReloadGame.Write/Read`), the bonus and the combo so a client's HUD draws the same thing.
- **Reticle HUD** (`UI/ReticleHud.cs`): the reload widget, low-ammo / RELOAD hint, Perfect tag and the combo counter, positioned at the reticle (screen centre in first person, the aim point from above).
- **Kill combos**: `Player.OnKill` chains kills within `comboWindow`; bonus sand dollars/XP per step (`comboSandDollars`, `comboXp`, capped at `comboMax`). `Player.Combo`, `ComboLeft`, `BestCombo`.
- `ViewModel` animates only from player state (ammo dropping = recoil, `SwingT`, `ReloadProgress`), so it works for online clients too.

## The campaign and Part II
- **`Campaign.asset`** (`Core/Campaign.cs`) lists the parts in order. A `PartDef` is a *Defense* part (one scene, Part I) or an *Assault* part (a list of `StageDef`s, one scene each). New parts go after Part II; an assault part needs its stage scenes (`ExpeditionBuilder` builds one case per stage) and its data. A stage sets its objective (`ObjectiveKind`: Spires, Beacons, Breach, Hold, Heart), the tide clock, the creatures and how fast they come, the difficulty (as a day of Part I) and its moonlit look (a `PhaseDefinition`; `PhaseManager.Hold` keeps it, with no day cycle). Endings (`EndingDef`) are the choices at the Heart.
- **A stage** (`World/Expedition.cs`) is a lane of seabed between two standing walls of sea. Its `Objective`s tick on the host; finishing one regroups the team (`ObjectiveDone`: a checkpoint, and the fallen get up); all done opens the `ExitGate`. Creatures step out of the walls (`creatureSpawns`) ahead of the expedition, faster while an objective raises `Pressure`. They hunt the nearest sailor (`GoalKind.Hunt`). `Arena.Seabed` makes the ground flat and dry.
- **Between stages** the run travels in its save: `NextStage` captures it with `stage + 1`, writes the slot, and `GameManager.Load(scene, Carry(...))` takes the local players' devices along. An online host sends `Reload(scene)`; clients follow, and ignore snapshots tagged with another scene's build index. The main menu starts a Part II save by loading its stage (`Expedition.SceneFor`).
- **Objectives**: `BroodSpire` (`IShootable`; explosions do 2.5×; hatches creatures near players), `Beacon` (stand by it to light it), `WreckBarrier` (only explosions count, a chain once; a gas-can cache nearby; three blasts), `HoldRing` (its clock runs only while someone is inside), `HeartAltar` (raises the Tidemother, then offers the endings through two `HeartChoice` interactables; the second needs every shard on the host's record).
- **Spiral Shards**: one `ShardStone` per stage, off the path. `ShardStone.Collect` keeps it in `Legacy` (a bitmask; every machine in an online game keeps its own) and lights a petal seat at the Heart; online the host sends `NetEvent.Shard`. Endings go out as `NetEvent.Ending`, and each machine records it.
- **Symbols** (`Glyphs`): unlit quads with a glyph texture (`Glyphs.Decal`, `DecalOn`; glowing ones are additive). `GlyphArt` draws the twelve glyphs from distance functions; setup saves them as PNGs. What each symbol means and where it goes is in `docs/STORY.md`; keep to it. Creatures with `EnemyDef.mark` carry the Mark on their backs.
- **The keep wall's tally** (`MenuScenery.Tally`): one scratch per run (`Legacy.Tally`), in fives; the Hull Graveyard lays one wreck per run in its `memorialField`. Both stop counting after the peace ending.
- **Story cards** (`UI/StoryCard.cs`): a part's opening lines (Part I's only on the very first run), each stage's title and epigraph, and the endings (the Spiral ending slides the Crest and the Mark together). Any key moves on; `StoryCard.Disabled` turns them off for tests.

## Online play
Host-authoritative, over **Unity Transport** (UDP). Two ways in: directly (LAN, or the internet with UDP port **7777** forwarded; optional room password) or with a **join code** through **Unity Relay** (encrypted with DTLS, no port forwarding). LAN games are announced by a beacon on UDP **47777**.

- **Channels** (`NetLink`): *reliable* (resent until delivered, in order: handshake, joins, banners, toasts, game over) and *unreliable* (newest wins, nothing waits for a lost packet: snapshots, input, cosmetic effects). Both fragment messages up to 64 KB. Everything runs on the main thread (`NetLink.Update` pumps the driver).
- **Movement is the host's.** Each client turns every frame of its players' controls into a numbered `NetCommand` (move, buttons, look; quantized exactly as it travels) and moves straight away (prediction). It sends every command the host hasn't confirmed yet (up to 24 per packet, 60 packets/s), so a lost packet costs nothing. The host runs each new command once, in order (`Player.RunRemoteCommands` → the same `StepMove` everyone uses), within a time budget that grows with real time (a sped-up client just runs out). Snapshots tell each client where its players are after the last command the host ran; the client starts from there and replays the rest (`Player.Reconcile`), and the camera eases across any difference (`RenderOffset`). Pushes, grabs and respawns happen on the host and reach the client the same way.
- **Snapshots** (20 Hz, unreliable): the shared state (phase, day, sand dollars, wall sections, powerplant, tidal cards and any vote, waves), every `NetPlayerState`, the client's own players' prompts/menus/confirmed movement, and the replicated things (`NetId`: creatures and corpses, gas cans, food, breakers, loot, defences) as a **delta against the newest snapshot that client confirmed** (it echoes the snapshot number in its input), plus the ids of everything that exists. Too old a confirmation, and every 40th snapshot, sends everything.
- **Events**: `Notices` (reliable: banners, toasts) and `Effects` (unreliable: sounds, particles, shakes, hit markers), batched per frame.
- **Menus online:** shop/hotdog menus run on the host (rows are mirrored, picking is input); pause/settings menus are local to the client (`Player.LocalMenu`) and never sent.
- **Enemy proxies** (`Enemy.SpawnProxy`, `Proxy = true`): no AI or damage; they glide to the host's pose, animate limbs from their own movement, drip from the host's wetness, sever the same limbs (bitmask) and turn into the same corpse (same `NetId`), which then follows the host (`NetFollow`) when carried or thrown.
- **Lifecycle:** "try again" sends `Reload`; clients reload, keep their join tokens, and the host re-assigns slots after its own reload (`NetHost.Rebind`). `Bye` (host quits, wrong password, wrong version) and lost connections return clients to the main menu with the reason.
- **Security** (the host never trusts the wire):
  - *Version check* in `Hello`; *room password* by challenge-response: the host sends a random salt and nonce, the client answers `HMAC-SHA256(PBKDF2(password, salt, 20000), host nonce + client nonce)`; the password never crosses the network; one try per connection, and on a direct game a wrong guess locks that address out for 2 s, doubling up to a minute.
  - *Relay games are encrypted* (DTLS) and need the join code. Direct games aren't encrypted (fine on a LAN; over the internet, prefer join codes).
  - *Limits*: 12 connections (including unfinished handshakes), 10 s to say hello, 64 KB per message, 400 messages/s per peer, 4 players per connection, 24 commands per packet; a peer that stops reading is dropped once 512 reliable messages are waiting.
  - *Validation*: a malformed message drops only that client; input only counts for players that connection owns; commands with NaN/infinity are ignored, movement/look/time steps are clamped, aim stays inside the world; names lose `<`, `>` and control characters and are cut to 16 characters (no rich-text injection into other players' HUDs); LAN beacons are sanitized and capped.
  - *Movement* comes from the host's simulation (no teleporting through walls), within real time (no speed hacks).
- **Wire format:** `NetProtocol.cs` documents it. Bump `NetProtocol.Version` when it changes; mismatched clients are turned away with a message.
- **Relay setup:** the project is linked to the Unity Cloud project "TideWall" (organization CheeseyDanish; `ProjectSettings.asset` → `cloudProjectId`). A fresh clone needs nothing else; to move it, link another project in Edit > Project Settings > Services. The free tier covers small groups. Each launch signs in anonymously with its own profile, so two copies on one computer are different players to the relay. Players sign in anonymously; nothing to configure for them. Without a link, "Host with a join code" explains this and LAN/address play still works.

## Roguelike systems
- **TidalCards** (on the GameManager): `OfferDraft()` when a `tidalDraft` phase starts (3 weighted picks from the cards allowed right now; an exclusive one 60% of the time when any is allowed), votes per player, `Resolve()` when everyone has voted or the timer runs out. Active cards multiply enemy HP/speed/damage, budget, sand dollars, XP, player damage/speed/max HP and corpse value, and can force wetness, add fog, extend breaker reach or shorten sand dollar life. `WaveFinished()` (from the WaveDirector, and at a fighting phase's end) counts them down.
  - Exclusive: `OnlineEligible` = players from 2+ owners (computers); `SplitEligible` = 2+ players with the same owner. Effects: `buddybeam` (the host draws tracers between players of different owners and burns enemies near the segment), `bottle` (a condiment status per wave, from another computer's player), `screenswap` (`PlayerManager` rotates viewports every 20 s; `DamageMult` x1.4 for players who share a screen), `snacks` (`Player.Eat` heals same-owner players; same-owner revives x2).
- **Progression** (in `Player`): `GainXp` → levels → `StatPoints`; `Allocated` points feed `StatBonus(StatKind)` (max HP, melee/gun damage, move speed, handling, fortune). Every `modEveryLevels` levels a `ModOffer` of `modChoices` mods for the weapons in hand; `Mods` (weapon id → mod ids) are applied by `RebuildWeapons()` to copies of the weapon defs (`EffGun`/`EffMelee`), which shooting and swinging use. `Respec()` refunds points for sand dollars.
- **Sand dollars**: `SandDollarPickup.Drop` scatters a creature's bounty; pickups slide to the nearest targetable player and pay the team purse x that player's Fortune.
- **Wall & powerplant**: `Wall` sections (`Add`, `Damage`, breach, `Repair`, `Grow`, `Restore`). The `WallSegment` model has **no end faces** on its long pieces (`open_ends` in the Blender script), so sections side by side form one seamless wall; `Wall.RefreshCaps` shows a `WallEnd` cap on any intact section next to a breached one, and a breached section is hidden and replaced by its `WallRubble`. Sally ports get a `WallGate` (solid pillars, open arch); `PowerPlant` (`Damage` → meltdown = `GameManager.GameOver`, `Repair`, `Grow`, `Restore`).
- **Runs**: `GameOver` deletes the run's save and calls `Legacy.Record`; `NewRun()` reloads with a fresh run in the same slot with the same local players (and the same online group).

## Menus, controls and animation
- **Menus** are data (`Menu`, `MenuItem`) with four layouts: `List` (pause, settings, stats, debug; drawn on the right of the viewport), `Grid` (shop, hotdogs, build: `GridView`, 3 columns of item cards with pictures from `Icons`), `Cards` (tidal card vote: `CardsView`) and `Table` (the casino: `TableView` draws `Menu.Board`, rich text read every frame so it can animate, on green felt above the list of actions; `Menu.Reels` adds `SlotsView`'s reel windows, lever, paytable and tide meter, and `Menu.Celebrate` the win effects). They're driven by the `MenuNav` action (d-pad, arrow keys, mouse wheel) so `Move` keeps walking; `Interact` picks, `Back` closes, `Swap`/`Reload` change tabs. A menu with an `Anchor` (a stall) closes when its player walks `AnchorRange` away. Online, a host-side menu's layout, tabs, item pictures/info and board are mirrored to the client (`NetIO.WriteMenu`). Protocol version 9 (players' snapshots carry the attachments on their gun; menus carry the reels and the celebration).
- **Icons** renders any model once with an off-screen camera (layer 30) into a cached sprite.
- **Player body**: `Part_LegL/R`, `Part_ArmL/R`, `Part_Head` are found by name and posed every frame in `Player.AnimateBody` (stride from speed, gun arm along the aim with the gun counter-rotated to keep pointing at the target, melee arm from `SwingArm` by `MeleeStyle`, carry/downed/dash poses).
- **Melee timing**: `MeleeDef.windup/strike/recover`; the hit (`Combat.Melee`) lands when the wind-up ends (`Player.Strike`). `SwingProgress` (0→1) drives both the body and the first-person view model.
- **Gunplay**: `GunDef.recoil` drives `PlayerCamera.Kick` (view snap + FOV punch, recovering), the view model's kick, muzzle flash and ejected shells (`Fx.Casing`), a little real aim climb (`Pitch`), and `FireHeat` (crosshair spread). `Fx.DamageNumber` (pooled world text, relayed online) and the HUD's hit/kill markers.
- **Guns locked**: `Player.GunsLocked` while `WaveDirector.RunWave < gunsUnlockWave`; Fire swings the melee weapon.

## Loot, defences, vendors
- **Loot** (`SandDollarPickup`, sand dollars and pearls): `Drop(at, total, killer)`. Pieces pop up, then fly at `lootFlySpeed` to the killer; any targetable player within `lootIntercept` of a piece catches it. No killer: land and slide to the nearest player. NetId kind `SandDollar` (def < 0 = pearl).
- **Defences** (`Structure`): built with `Structure.Build(def, pos, yaw)` from build mode (`Player.StartBuilding` → `UpdateBuild`: preview ghost on the player's view layer, `Structure.WhyNot` placement rules, `GameManager.TrySpend(sd, pearls)`). Barricades push creatures out and are chewed (`Enemy.blockedBy`); spikes hurt; snares call `Enemy.Snare`; bait is found with `Structure.BaitFor`; turrets and cannons aim their `Part_Head` and fire (`Lob` for cannon shells). NetId kind `Structure` (HP and head rotation replicated). Saved in `SaveData.structures`.
- **Vendors** (`Vendor`): scenery only, local on every machine; lines from `GameDatabase.chefLines` / `fishmongerLines` (the casino crab's from `Casino.CrabLines`).
- **Gun attachments** (`AttachmentDef` in `GameDatabase.attachments`; `Player.Attachments`, gun id → ids, in `Player.Attachments.cs`): one per `AttachmentSlot` per gun (`Attachment`: a part with an `AttachmentMount`; `Ammo`: element, pierce, blast, limb bonus), bought from the shop's Attachments tab (`Player.FitAttachment`). `RebuildWeapons` folds their multipliers into `EffGun` after the mods. `Player.DressGun` puts the attachment's model (`Att*`, placed by its mount) on the gun model and the view model, placed from the muzzle socket. Saved as `PlayerSave.attachments` ("gunId/attachmentId"); sent in `NetPlayerState.attach` for proxies' models. Setup merges new default attachments into an existing GameDatabase asset (and replaces entries from before the two-slot layout).
- **The casino** (`Casino`, on the GameManager, host only): one `CasinoGame` per player per game (`Casino.Seat<T>`), so a hand in progress waits if you walk off. Games take stakes with `Casino.Stake` (the team purse) and pay with `Casino.Pay` (stake + winnings); timed parts (reels, the wheel, Fathoms' step-by-step reveal) run in `CasinoGame.Tick`; `CasinoGame.Cheer` starts a win's celebration. Slots: three fixed 25-symbol strips (`Slots.Strips`, from the weights), a spin picks a stop per reel; reel positions are continuous (ease-out, then a damped bounce) and `SlotsView` draws the symbols' model pictures (`Icons`) at those positions; `Slots.SimulateReturn` gives the long-run return with High Tide. `Casino.Closed()` keeps Part I's tables shut while a phase isn't `shopOpen`. Cards come from a `Shoe` (`Stack` puts known cards on top for tests). `CasinoBooth` is the town booth and the seabed crate. `Menu.OnSide` (left/right on rows without their own adjust: the bet) and `Menu.Quick` (the Reload button: `CasinoGame.Repeat`, labelled by `RepeatLabel`, sent online as `QuickLabel`) make a round one press.
- **Debug tools** (`DebugTools` + `DebugMenu`): static switches read by the game (`Player.TakeDamage` god mode, `Player.Shoot` ammo, `Player.Noclip` flying with the CharacterController off, `Enemy.Update` freeze, `GameManager.Update` time scale). Opened with F1 (the keyboard player) or the pause menu; offline and on the host only; Settings → Debug tools hides it. Debug-only hooks are named `Debug…` (`Objective.DebugComplete`, `Expedition.DebugRefillTide`, `WaveDirector.DebugSkipQueue`, `Legacy.DebugWrite`, `Player.DebugRefill`). The legacy editor edits a copy and writes `legacy.json` only on Write.
- **Thieves**: `WaveDirector.SendThieves` (phase `corpseThieves`) spawns gulls with `Enemy.MakeThief`; they parent a corpse (`Corpse.Thief`) and fly out to sea; killed, they drop it.
- **Corpses**: `Enemy.LiftCorpse` raises a tipped-over model so it rests on the sand; corpses have a larger interaction radius and `Corpse.Point` is the model's centre; first-person players pick up what they look at (`Player.LookedAt`).

## Visuals
- Procedural sky (`Content/Materials/Sky.mat`, Skybox/Procedural) tinted per phase by `World.SetSky`; cameras clear to it and get the graphics settings every frame (`World.SetupCameraSky` → `GraphicsApply.ConfigureCamera`).
- **Main menu**: `GraphicsApply.MenuBoost` (set by `MainMenu.Show/Hide`) renders the menu at 2x scale with MSAA 8x in builds. The runtime pipeline copy is made from the best quality level's asset (PC) and re-assigned after every quality change, so the "Quality preset" never swaps in the Mobile pipeline. `Settings.version` 2 resets the old quality preset (older files picked Mobile).
- **World text** (stall signs, name tags, vendor speech, damage numbers) is 3D TextMeshPro (`Ui.Label`; depth-tested, so walls hide it) with a `Billboard`, which turns it to face each camera just before that camera renders (`RenderPipelineManager.beginCameraRendering`), so every split-screen player reads it the right way round.
- **Graphics settings** (`GraphicsApply`): resolution/display mode/VSync/frame cap (`Screen`, built game only), render scale, MSAA and shadow distance/cascades on a **runtime copy** of the URP asset (built game only, so the editor's assets never change), FXAA/SMAA and post-processing per camera, bloom on a runtime copy of the scene Volume's profile, sun shadows, draw distance (far clip), particle density (`Fx.Emit`). Defaults: native resolution, borderless fullscreen, MSAA 4x, high shadows.
- **Breakers**: the curl model, spray (`Fx.Spray`, local), riders on surfboards (`Enemy.ShowBoard`, replicated via enemy flag 32), wipeouts (`GameDatabase.breakerWipeoutChance` → `Enemy.WipeOut`).
- Sea: a 2.5 m grid with rolling waves, breaker swells (steep front, long back) and a moving foam line at the shore. Wet sand is glossier.
- Clouds, kelp, shells, starfish and sandcastles are scattered at build time from a fixed seed. Particles use a soft round sprite. The powerplant's steam (`Fx.Steam`) is made locally on every machine.

## Saves and settings
- `Storage.Root` = `Application.persistentDataPath` (Windows: `%USERPROFILE%\AppData\LocalLow\<company>\TideWall`). Writes go to a temp file first, then replace the old one.
- `settings.json`: `Settings` (audio, game, online name/address/port, binding overrides). `Settings.Changed()` clamps, applies (volume, fullscreen, quality) and saves; `Settings.OnChanged` lets cameras, audio and every `PlayerControls` react.
- `saves/slot1..3.json`: `SaveData` (version 2), captured by `SaveSystem.Capture` when a `saveOnStart` phase begins, or from the pause menu during it. Restored by `GameManager.StartRun` (sand dollars, team, wall sections, powerplant, tidal cards, day, phase) and `Player.RestoreLoadout` (weapons, level, XP, stat points, mods, by player slot). Deleted when the run ends.
- `legacy.json`: `Legacy` (runs, best day, best level, kills).
- **Rebinding** (`Rebinder`) runs `PerformInteractiveRebinding` on a device-less copy of the default map, restricted to keyboard + mouse or gamepad + joystick controls, and stores the result as an override keyed `Action/Group/Part`.

## Data assets
`GameDatabase` and `PhaseCycle` are ScriptableObjects in `Assets/Content/Data` (referenced by the content library). Their defaults are in code (`FillDefaults()`); the setup step writes them as assets the first time.
- Tune by editing the assets in the Inspector.
- If you change a default in code, run **TideWall → Reset Data To Defaults** (or edit the asset too). The asset wins at runtime (CLAUDE.md R1).

## Model pipeline
```bash
blender --background --factory-startup --python Blender/generate_models.py -- <repo root>
```
The Blender executable on this machine is `C:\Program Files (x86)\Steam\steamapps\common\Blender\blender.exe`. The script writes `Assets/Content/Models/<Name>.fbx` (then run TideWall → Setup Project to add new ones to the content library) (FBX, -Z forward, Y up, transforms baked). The `ModelImport` postprocessor turns off animation, cameras and lights and keeps the flat normals.

The website's `.glb` models (`Blender/source/`) are imported, scaled to a target size and set on the ground. Their duplicate vertices are welded, and anything over ~8k faces is decimated. Welding has to come first: the Glizzy Monster sculpt is stored as split triangles, and decimating it without welding shreds it. That sculpt is also untextured white, so the script colours it like a sausage.

Conventions (CLAUDE.md R4–R6): front faces -Y in Blender; `Limb_<Part>` objects have their pivot at the joint; `Socket_<Name>` empties mark hands, muzzles and the keep's menu camera (`Socket_Camera`); a material named `coat` is recoloured per player.

## Performance notes
- One shared `ParticleSystem` per effect type: drips, gore, sparks, smoke, fire, splash, ink, bubbles, debris. Calls are `Emit`-style, never per-enemy systems.
- Tracers (`LineRenderer`) and flash lights are pooled.
- `GameDatabase.maxAlive` caps live enemies (70).
- The sea is a CPU-animated grid (~4k vertices).
- Physics queries use non-alloc buffers. Explosions use their own buffers, because they can fire inside a shot or swing loop when a gas can goes off.
- Online: snapshots send only entities whose bytes changed since the client's last confirmed snapshot, so a beach full of still corpses costs little after the first one. Input commands are 23 bytes each.
- The HUD rebuilds a line of text only when the values in it change (`PlayerHud.HudLine`, `Ui.Set`), so a steady HUD allocates nothing per frame.
